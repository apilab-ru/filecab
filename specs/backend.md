# Backend

## Purpose

Define private library APIs, Google sessions, extension replication, sharing and
parser configuration. Requirements are mandatory unless marked optional.
See [Stack](stack.md), [Domain contracts](domain-contract.md), [Catalog](catalog-spec.md)
and [Backend implementation decisions](../implementation/backend-decisions.md).
Delivery status belongs in the [checklist](../implementation/requirement-checklist.md).

## Accounts and sessions

### Google authentication

Use Google login only; no password registration or reset. Identify accounts by verified
Google `sub`, not email. Validate authorization, issuer, audience, expiry, state and nonce;
keep client secrets on the backend.

### Website and extension login

Start website login by redirect and extension login through `identity.launchWebAuthFlow`.
Use production HttpOnly/Secure cookies with SameSite and CSRF protection for the website.
Extension callbacks carry a short-lived, single-use code bound to the login attempt
by a verifier/challenge. Allowlist callbacks; never place reusable credentials in URLs
or expose them to content scripts.

### Session lifecycle

Support account lookup, refresh, logout and all-session revocation. Use short-lived
extension access tokens and rotating refresh credentials with replay detection.
Hash opaque server-side credentials. Lifetimes, concurrency and exchange contracts are
specified in [Authentication decisions](../implementation/backend-decisions.md#google-authentication).

## Library identity and data

### Independent entry identity

CRUD addresses immutable entry UUIDs, optionally generated by clients. Keep owner,
category, optional internal `catalogId` and namespaced string provider references separate.
Follow [Domain contracts](domain-contract.md); equal provider numbers do not prove identity.

### Library fields

Use the fields, categories, statuses, rating/progress limits and installment boundaries
in [Product data rules](functionality.md#3-domain-identity-and-validation).
Keep snapshots, notes, viewing links, timestamps, server version and deletion state.

### Ownership and duplicate protection

Derive ownership from authenticated credentials, never submitted owner/entry IDs.
Allow at most one active entry per owner and internal catalog item.

## Viewing sources

### Multiple viewing links

Keep multiple HTTP(S) viewing sources separate from catalog links. Preserve original
and normalized URLs using [Source normalization](../implementation/baseline-decisions.md#viewing-source-normalization).
Only verified site adapters may normalize episode paths or remove allowlisted tracking
parameters. Home/search URLs do not prove media identity. One normalized source may
belong to one active entry per owner; reassignment is explicit and atomic.

## Library operations

### Create, read, update, and delete

Provide owner-scoped create/read/list/update/delete/restore. Updates and deletes
require expected server versions. Commit entry/source changes atomically and publish
them to replication. Semantic edits update modification time; no-ops and catalog
refresh do not. Client timestamps never determine replication order.
See [Mutation contracts](../implementation/backend-decisions.md#owner-library-api).

### Delete and undo

Delete through tombstones. A 10-second Undo restores the exact entry after ownership,
version and current catalog/source uniqueness checks.

### Retrieve the complete owner library

Return all active owned entries, including hidden entries and searchable metadata;
exclude tombstones from ordinary snapshots. Do not accept display filters, ordering or
pagination on this endpoint. The website caches the snapshot in memory; the extension
queries RxDB. Replication transport batches are independent of display pagination.
Catalog and shared-list retrieval use separate contracts.

### Client-side search, filters, sorting, and pagination

Apply [Library browsing rules](functionality.md#6-library-browsing) to the complete owner
dataset: filter, stable sort, then paginate. Display totals count all matches, not just
the page. Reset pages after filter/sort/size changes and clamp them after data changes.
Default page size is 20; supported sizes are 12, 20, 50 and 100.

## Catalog search and details

### Provider adapters

Use the independently configurable providers, deployment defaults, capability checks
and activation requirements in [Catalog](catalog-spec.md). Catalog availability must
not gate manual CRUD. Shikimori is a list-sync connection, not a catalog provider.

### Search contract

Follow [Catalog search](catalog-spec.md#search-contract) and
[Pagination integrity](catalog-spec.md#pagination-integrity): one-based pages,
limits 1–50, enforced category/locale/filter support, exact totals only when known,
and continuation based on deliverable normalized results.

### Catalog identity and metadata refresh

Separate internal detail lookup from provider-reference resolution. Upsert verified
namespaced identities concurrently and preserve provenance. Missing fields must not
erase known metadata; refresh must not overwrite user fields or remove saved entries.
See [Identity](catalog-spec.md#identity-and-cross-provider-references) and
[Enrichment](catalog-spec.md#details-and-safe-enrichment).

### Genres

Use stable internal genre IDs, localized labels and verified provider mappings.
Preserve unknown mapping data without rejecting the media record. Genre refresh is
an authenticated operator action, never a public mutating GET.

## Matching and enrichment

### Candidate identification

Match in order: internal catalog identity, verified provider references, normalized
saved sources, then title suggestions. Preserve season/year/edition/format distinctions.
Only verified identity recognizes entries automatically; one candidate or similar text
is not proof.

### Manual entry reconciliation

Allow later catalog association. If that identity is already saved, preview the survivor,
field choices and source associations. Apply merges atomically with expected versions
and tombstones for removed entries.

## Extension offline data and synchronization

### Durable local extension state

RxDB is the device library source of truth. Support offline manual CRUD, browsing,
filters, import/export and available snapshots; report catalog-dependent work as offline.
Acknowledge only durable saves. Preserve pending changes across interface closure,
browser restart and worker suspension. Failed reads enter recovery without overwriting data.

### RxDB pull and push

Implement native RxDB replication: stable IDs, tombstones, checkpoint pull,
assumed-master-state push and conflict responses. Use RxDB metadata rather than a
second client outbox. Scope batches to the authenticated owner, validate fields and
compare server versions atomically. Separate invalid writes from conflicts.
[Transport decisions](../implementation/backend-decisions.md#replication-transport)
define limits, ordering and partial-batch commits.

### Commit-safe change tracking

CRUD, replication, imports, merges, deletes and restores use the same mutation rules
and publish changes atomically. Serialize owner revisions through commit; timestamps
or sequences allocated before commit cannot prove commit order. Transport cursors
must not lose JavaScript integer precision.

### Conflict recovery

Keep the current server document on stale-version conflict. Persist rejected local
intent for visible, deliberate reapplication; client and server policies must agree.

### Sync lifecycle and retention

Replicate on opening, local changes, reconnect and manual refresh only for the explicitly
linked authenticated account. Scope metadata by account/schema; never submit another
account's pending edits. Live transport is optional. Retain history/tombstones for at
least 90 days; the current implementation keeps them indefinitely until verified cleanup
exists. Expired/unavailable checkpoints return `SYNC_RESET_REQUIRED`; reset preserves
pending intent and prevents resurrection.

### Guest adoption

Keep one fixed-name device library visible across login, logout and account changes,
including unsaved input. Linking/importing requires a revision-bound preview, explicit
confirmation, identity/source conflict checks and retry-safe writes.

## Unlisted read-only sharing

### Sharing controls

Owners can enable, inspect, disable and rotate an anonymous read-only link. Tokens need
at least 128 bits of cryptographic entropy and server-side hash storage. Return plaintext
only at creation/rotation; replace an unrecoverable token instead of reconstructing it.

### Shared data projection

Allowlist title, category, available poster/year/format, status, rating and progress.
Exclude hidden/deleted entries, notes, viewing URLs, account/email data, sessions and
replication metadata. Apply filters/order/counts only to this projection. Tokens grant
no mutation, owner-lookup or sync access. Shared pages have no persistent offline library.

### Shared freshness and privacy

Serve committed data with `Cache-Control: no-store`, noindex and a restrictive referrer
policy. Redact tokens; unknown/revoked links receive non-enumerating not-found responses.
Exclude shared lists from discovery/sitemaps. Revocation blocks later requests but
cannot retract already viewed/copied content or promise immediate removal from an open page.

## Backup and restore

### Export and import formats

Use [Backup rules](functionality.md#8-backup-and-restore) and the
[v1 format](domain-contract.md): active entries, preserved identities/user data/sources/
metadata/timestamps, no account/settings/credentials/server versions/deletion state.
Reject unknown fields, invalid dates, identity/source conflicts, legacy formats and
files over 10 MiB. Do not infer missing data or silently discard invalid entries.

### Preview and atomic replacement

Require validation, counts/conflicts, a downloadable pre-restore backup and confirmation
bound to owner, payload digest and library revision. Empty replacement needs separate
confirmation. Apply atomically and publish tombstones; failures preserve the library.
Keep settings/sharing separate. Ordinary synchronization never replaces the whole library.

## English and Russian metadata

### Locale-aware API

Require explicit `en` or `ru` for catalog search/detail/genres; reject missing or unsupported
locales. Preserve field language/provenance, including unknown, and stable identities
across locales. Original title is not automatically English.

### Preserve user text

Keep user titles, notes, links and remote query text unchanged, except documented
provider-required query encoding. Locale changes and refreshes never rewrite user data.
Machine translation and universal cross-language search are optional.

## Server-managed parser configuration

### Declarative extraction configuration

Serve versioned hostname/path mappings, selectors, approved attributes, known fields and
fixed fallbacks for the bundled extraction engine. Never serve executable JavaScript,
expressions or remote interpreter commands. New capabilities require an engine release;
configuration cannot grant permissions or trigger background browsing collection.

### Configuration compatibility and rollback

Include schema/revision, engine compatibility and HTTP cache validators. Cache the last
valid configuration and bundle defaults. Publication requires authenticated operators,
fixture checks and audit history; support rollback.

### Page data minimization

Extract in the extension after user interaction. Send only necessary structured metadata
to matching, not full HTML/history. Page parsers and catalog providers are independent.

## API contracts and operational behavior

### Validated, versioned contracts

Use versioned REST contracts and runtime DTO validation. Enforce ownership, allowlists,
sizes, enums, IDs, HTTP(S) sources, pagination and batch limits. Define optional/null/
clearing semantics; TypeScript types alone do not validate requests.

### Actionable errors

Return stable code, HTTP status, correlation ID, retryability and optional value-free
validation details. Distinguish auth, validation, conflict, throttling, service failure
and empty results. Never return stacks, credentials or private payloads.

### Provider resilience and cache

Bound timeouts, response sizes, concurrency and retries; honor provider rate limits.
Key catalog/genre caches by locale and exclude private library data. Configure freshness
TTLs and identify stale fallback. Full shared rules are in [Catalog](catalog-spec.md).

### Secure operations

Validate configuration at startup, enforce exact-origin CORS/CSRF, require production
HTTPS and restrict operator actions. Redact credentials, codes, tokens, notes and page
contents from logs. Liveness is provider-independent; readiness checks the database.
Separate development/production credentials and storage; test migration/backup recovery.

### Swagger API documentation

Generate OpenAPI with `@nestjs/swagger`: UI `/api/docs`, JSON `/api/docs-json`.
Document actual parameters/bodies, responses/statuses, validation/nullability, anonymous
and authenticated endpoints, safe errors and synthetic examples. Support Filecab bearer
auth; explain cookies/CSRF separately. Update DTOs and docs together. Enable local docs;
production defaults and HTTP details follow
[API foundation](../implementation/backend-decisions.md#api-foundation).

## Verification

Test ownership, identity collisions, concurrent duplicates, stale versions, atomic sources/
merges/restores, delete/Undo, commit-safe checkpoints, batch retries, rejected-intent
recovery, account switching, history reset, OAuth replay, sharing privacy/revocation,
locale fallback, provider failure and parser rollback. Use deterministic fixtures;
authorized live checks supplement them and must be reported separately.
