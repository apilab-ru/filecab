# Filecab

The [specification](specs/index.md).

## Setup

Requires a supported Node.js 22.12+ release (CI uses Node 24), pnpm 12.16.1, and PostgreSQL 17 for database checks. Run these commands from the repository root:

```sh
npm install -g pnpm@12.16.1
pnpm install
cp -n apps/api/.env.example apps/api/.env
```

## Development

```sh
pnpm dev:web        # React + Vite, http://127.0.0.1:5173
pnpm dev:extension  # WXT + React (Chrome)
pnpm dev:api        # NestJS, http://127.0.0.1:3001
pnpm dev            # Website + API
```

See the [extension README](apps/extension/README.md) for loading the extension in Chrome and debugging it.

## Build and check

```sh
pnpm build
pnpm typecheck
pnpm format        # Format supported source, config and documentation
pnpm format:check  # Check formatting without changing files
```

The root install enables the Husky pre-commit hook. It formats staged files with
Prettier through lint-staged, preserving unstaged edits. Run `pnpm prepare` to
reinstall the hook if needed. Generated files, lockfiles and local environment
files are excluded; CI runs `pnpm format:check`.

Nx also accepts individual targets: `pnpm exec nx build web`, `pnpm exec nx build extension`, `pnpm exec nx build api`, and `pnpm exec nx typecheck library`. Libraries have build and typecheck targets too.

- `apps/web`: minimal React page with Vite.
- `apps/extension`: WXT popup, full page (`full-page.html`), background, and content script. The empty content script matches only `https://example.com/*`.
- `apps/api`: NestJS bootstrap with validated server configuration and backend-only Prisma client factory. Health, Google login, session and owner-library endpoints live under `/api/v1`; `/` returns 404. Override the port in `apps/api/.env`.
- `packages/ui`: shared React panel.
- `packages/library`: shared React placeholder composed from UI and contract types.
- `packages/contracts`: framework-independent TypeScript types.

## Configuration

Edit `apps/api/.env` with local credentials before starting the API. It loads that
file independently of the working directory; existing environment variables take
precedence. Startup fails with field names only if configuration is invalid.
Integrations default to disabled and require no real Google/provider credentials.
Google login is available when its OAuth credentials are configured. Catalog and external-list provider workflows remain in their planned implementation steps.
Optional API error reporting uses `SENTRY_DSN`; leave it empty to disable Sentry. The
API reports server errors with HTTP method and route template; request bodies,
parameter values, headers, user, breadcrumb and extra data are excluded.

Use separate database names ending in `_dev` and `_test` for development and test;
production must use neither suffix. Production requires HTTPS web/callback
origins and independent base64-encoded 32-byte session/encryption keys. Generate
each key locally with `openssl rand -base64 32`; never reuse example credentials.

Optional client examples are in `apps/web/.env.example` and
`apps/extension/.env.example`. Only public API origins belong there. Never put
server credentials in `VITE_` or `WXT_PUBLIC_` variables. Authentication clients consume these origins; keep local website/API hosts consistent (use `127.0.0.1` for both).

## PostgreSQL and migrations (macOS)

```sh
brew install postgresql@17
export PATH="/opt/homebrew/opt/postgresql@17/bin:$PATH" # Intel Macs: /usr/local/opt/...
pnpm db:start
createuser --pwprompt filecab_dev
createdb --owner=filecab_dev filecab_dev
createuser --pwprompt filecab_test
createdb --owner=filecab_test filecab_test
```

Set `DATABASE_URL` in `apps/api/.env` to your development database, URL-encoding
special characters in credentials. Homebrew service commands affect the whole
PostgreSQL 17 service: `pnpm db:service-status` inspects it and `pnpm db:stop` stops
it without deleting databases. `db:start` does not enable startup at login.

```sh
pnpm db:generate  # Backend-only generated source; no database required
pnpm db:validate  # Validate schema/configuration
pnpm db:deploy    # Apply committed migrations; do this for a new database
pnpm db:status
pnpm db:migrate   # Create future development migrations; never use on production
```

The initial migration creates only the `workspace_state` infrastructure marker.
Later migrations add accounts, separate libraries, entries, source claims, catalog metadata and change history.
Generated Prisma source is ignored by Git and generated by API build/typecheck.
Migration commands load `apps/api/.env`; a shell `DATABASE_URL` overrides it.
Use deployment secrets and `db:deploy` in production, never local dev credentials.

## Verification

```sh
pnpm check:boundaries
pnpm test                    # Unit tests
pnpm test:contracts          # Workspace dependency contract (domain contracts follow)
pnpm typecheck               # Includes infrastructure configs/tests through Nx checks
pnpm build
```

Database tests require an explicitly selected dedicated PostgreSQL 17 test database
and do not auto-load a development `.env`. In a shell, set `DATABASE_URL` to your
`filecab_test` connection and `NODE_ENV=test`, then run:

```sh
pnpm db:deploy
pnpm db:status
pnpm test:integration
```

Missing/unreachable databases fail the suite instead of skipping it. The suite
checks committed migration state, generated-client queries, PostgreSQL version,
migration-marker persistence, owner isolation, duplicate races, version checks, atomic library mutations, change ordering and database readiness.

```sh
pnpm exec playwright install chromium
pnpm test:e2e
```

Playwright starts the Vite website and checks that it renders without extension
APIs or browser exceptions. Later steps add product workflows and extension E2E.
Nx equivalents include `pnpm exec nx test checks`, `pnpm exec nx test-contracts
checks`, `pnpm exec nx test-integration checks`, and `pnpm exec nx test-e2e checks`.
CI runs all suites, builds, and typechecks against a PostgreSQL 17 service with
synthetic credentials; it needs no live provider or Google credentials.

The boundary checker inspects manifests, imports/re-exports, dynamic imports, and
TypeScript path aliases. Client projects cannot depend on API/Prisma/server-only
modules or import environment files; shared UI/contracts cannot depend on client
data adapters. Non-literal module loading is rejected because it bypasses static
checks. Changes to architecture must update the specs and boundary rules together.

## API foundation

Run `pnpm dev:api` after configuring `apps/api/.env`. The listener binds to
`127.0.0.1:3001` by default. Available routes are:

- `GET /api/v1/health/live`: process liveness without database/provider access.
- `GET /api/v1/health/ready`: bounded PostgreSQL readiness probe; 503 on failure.
- `/api/docs` and `/api/docs-json`: Swagger UI and OpenAPI, outside production only.

Health endpoints are anonymous and accept no query parameters. Google authentication, session and owner-library endpoints are described below. Every response has an
`X-Correlation-ID`; errors include a stable code, HTTP status, safe message,
correlation ID and retryability. The JSON body limit is initially 1 MiB.

Set exact `WEBSITE_ORIGINS` and `EXTENSION_ORIGINS` allowlists; leave extension
origins empty until the extension ID is known. Unsafe cookie requests require
an allowlisted `Origin` and `X-Filecab-Request: 1`. A bearer header does not bypass
this check when cookies are also present. Request DTOs reject unknown fields
and implicit coercion. OpenAPI describes actual routes and their bearer/cookie schemes.

Production requires a local HTTPS-terminating proxy forwarding to the loopback
listener. Replace incoming `X-Forwarded-Proto` with the proxy's actual scheme;
only loopback proxies are trusted. Plain HTTP is rejected and HSTS is emitted.
Send readiness/liveness probes through that HTTPS proxy. Swagger UI, JSON and
YAML routes are unavailable in production. Restrict access to the internal listener.
Configure proxy access logs to omit URLs/query strings, cookies, authorization,
request bodies and upstream error payloads. The API logs only request IDs,
methods, statuses and durations, and reports invalid configuration field names without their values; unexpected startup failures use a generic message.

New endpoints must add explicit request DTO validation and OpenAPI response
schemas together, including field bounds, nullable/clearing semantics, errors
and anonymous versus authenticated access. Keep synthetic documentation examples
free of account data and secrets.

## Google login and sessions

Create a Google **Web application** OAuth client and add this exact authorized
redirect URI for local development:

```text
http://127.0.0.1:3001/api/v1/auth/google/callback
```

Set `GOOGLE_ENABLED=true`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` and
`GOOGLE_CALLBACK_URL` in the private API environment file. For local storage
outside the repository, use `~/.config/filecab/api.env` with permissions `600`
and link `apps/api/.env` to it. Existing environment variables take precedence.
Use a separate production Google callback URL and register it exactly in Google
Cloud. Do not copy Google client secrets to either browser application's environment.

Apply migrations with `pnpm db:deploy`, run `pnpm dev`, then open
`http://127.0.0.1:5173/` and choose **Sign in with Google**. Complete Google's
consent screen yourself. The website receives only HttpOnly cookies; no reusable
credentials appear in its redirect URL or JavaScript storage. Production cookies
use `__Host-` names and Secure, Path=/, SameSite=Lax, with no Domain attribute.
HTTP development uses unprefixed names and HttpOnly/SameSite=Lax/Path=/.

| Route under `/api/v1/auth` | Access and purpose                                        |
| -------------------------- | --------------------------------------------------------- |
| `GET /google/start`        | Anonymous, allowlisted return URL and browser-bound login |
| `GET /google/callback`     | Google state/nonce/code validation and safe redirect      |
| `GET /extension/config`    | Anonymous Google/extension-origin readiness check         |
| `POST /exchange`           | Extension one-use code plus verifier/attempt              |
| `GET /me`                  | Website access cookie or extension bearer access token    |
| `POST /refresh`            | Website refresh cookie or extension JSON refresh token    |
| `POST /logout`             | Revoke current authenticated session                      |
| `POST /logout-all`         | Revoke all sessions for the authenticated owner           |

Access lasts 15 minutes by default; refresh families have a 30-day absolute and
7-day idle limit. Validated `AUTH_*_SECONDS` settings may shorten these lifetimes.
Refresh rotates tokens atomically, retains consumed hashes and revokes a family
if a consumed credential is reused. A lost refresh response may require login.
Clients serialize refresh; the website coordinates tabs with Web Locks and clears
private query/mutation caches on account changes. Sign-out updates other open tabs.

The extension uses `identity.launchWebAuthFlow`; add its exact
`chrome-extension://<32-character-id>` to API `EXTENSION_ORIGINS` before login.
Its callback is `https://<id>.chromiumapp.org/filecab`; Google still returns first
to the API's configured Google callback URL. Refresh credentials are restricted
to trusted extension local storage; access tokens and login attempts use trusted
session storage. Popup/full-page messages receive account state only. Guest
library adoption, offline library storage and replication remain later steps.

Automated signed-token, HTTP/PostgreSQL, client and cross-tab browser tests cover
the authentication rules. Live Google consent and Chrome identity-window login
require a separate manual check; reaching Google's sign-in screen does not prove
a completed code exchange.

For extension login failures, see the [extension debugging guide](apps/extension/README.md#debugging-sign-in). It explains worker versus popup DevTools, safe stage diagnostics, exact origin setup and the real Chromium extension regression test.

## Owner library API

The authenticated routes below are relative to `/api/v1` and use the owner from
the access cookie or extension bearer token. No route accepts a submitted owner or client snapshot.
Catalog providers can be disabled while creating and editing manual entries.

| Method and path                              | Request / result                                                                             |
| -------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `GET /library`                               | Complete active private library and revision; includes hidden entries, excludes tombstones.  |
| `GET /library/entries/:entryId`              | Active owned document; deleted or foreign entries return 404.                                |
| `POST /library/entries`                      | Editable fields and required category; optional UUID/catalogId. Returns the server document. |
| `PATCH /library/entries/:entryId`            | `expectedVersion` plus editable fields.                                                      |
| `DELETE /library/entries/:entryId`           | `expectedVersion`; returns the deletion tombstone.                                           |
| `POST /library/entries/:entryId/restore`     | Tombstone `expectedVersion`; restores unless identity/source claims conflict.                |
| `POST /library/merges/preview`               | Survivor/removed IDs and versions, plus `fields` choices.                                    |
| `POST /library/merges/apply`                 | The same choices plus `previewToken`.                                                        |
| `POST /library/sources/reassignment/preview` | From/to IDs and versions, plus the saved `normalizedUrl`.                                    |
| `POST /library/sources/reassignment/apply`   | The same source movement plus `previewToken`.                                                |

Request/response schemas and synthetic examples are available in `/api/docs`
outside production.

A manual creation body can be as small as:

```json
{ "category": "anime", "userTitle": "My manual entry" }
```

The server generates the UUID and timestamps. An existing internal `catalogId`
loads metadata from the server; a caller cannot submit a snapshot. Manual titles
must remain nonblank. User text is preserved exactly. Ordinary PATCH cannot
change catalog identity, creation time or snapshot metadata.

Versions are canonical positive decimal **strings**. Updating a document with
its current version and unchanged fields is a no-op. Status null clears status;
rating/progress zero, an empty comment and an empty source list are explicit
clearing operations. Progress above a known total is retained without an
automatic status change; UI warnings/editing controls follow in step 11.

Snapshot revision and entries come from one RepeatableRead transaction. Display
search, filters, sort and pagination stay client-side; query parameters on owner
routes are rejected. The stable transport order by UUID is not a display sort.

Previews return current/proposed documents with null `serverVersion` on unsaved
proposals. Their HMAC confirmation expires after five minutes and binds the owner,
operation, versions, source order and choices. Apply revalidates everything under
the same library lock used to publish all affected changes. A stale, altered or
expired preview returns 409 without partial writes. Merges preserve the selected
survivor identity and tombstone the removed identity; source lists are combined
without truncation. A result above 100 sources is rejected until sources are
reduced explicitly. Website cookie mutations also require the existing Origin
and `X-Filecab-Request: 1` protections.

This is the API delivery; library screens, offline persistence, replication and
Undo dialogs remain in their planned later steps.

## Extension offline storage

The extension popup and full page now save manual library entries locally with
RxDB/Dexie in the fixed `filecab-local` database, revision checks and ten-second
Undo. The same entries and editor remain visible after sign-in/sign-out; local
reads/writes work without the API or a running service worker.
Failed reads show recovery with retry/raw export; failed writes retain editor
input. See [local storage details](apps/extension/README.md#local-library-storage).
Account replication starts only after an explicit linking preview and confirmation; see [extension synchronization](apps/extension/README.md#account-synchronization).

## Replication API

Authenticated `POST /api/v1/replication/pull` accepts
`{ "schemaVersion": 1, "checkpoint": null, "limit": 100 }` and returns complete
changed documents, a checkpoint and `hasMore`. Reuse the returned checkpoint for
subsequent pulls, continuing while `hasMore` is true. Limits are 1–100 and cursors
are decimal strings. Changes include deletion tombstones; repeated revisions of
one entry in a batch collapse to the last state.

`POST /api/v1/replication/push` accepts
`{ "schemaVersion": 1, "rows": [{ "assumedMaster": null, "proposed": entry }] }`.
Use the full last server document as `assumedMaster` for updates. Each of 1–100
distinct entry IDs commits independently. Stale assumptions return conflicts with
the current owned document. Equivalent retries are no-ops. Invalid request shapes
fail before writes; semantic failures stop the batch after any preceding commits.
Retry the original batch after uncertain outcomes. Snapshots are authoritative
server metadata and cannot be edited through replication. Cookie authentication
requires the same CSRF controls as the library API; bearer authentication is
supported. See `/api/docs` for full schemas.

A `SYNC_RESET_REQUIRED` error signals an unavailable history position or a future
checkpoint. History and tombstones are currently retained indefinitely. The extension
uses native RxDB replication metadata, preserves rejected edits for deliberate review,
and offers explicit recovery before replacing a stale replica. Signing in does not
start synchronization or upload the device library.

Run `pnpm test:replication` with an explicitly selected disposable `DATABASE_URL`
and Chromium installed (`pnpm exec playwright install chromium`). It builds the
extension and tests real Chrome messaging/native RxDB against the authenticated
API and PostgreSQL. Google identity is synthetic; no live consent is claimed.
`pnpm test:e2e` separately covers native protocol fixtures, browser restart,
missing history, failed recovery writes and account switching. CI runs both checks.
